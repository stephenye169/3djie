# 青果巷 · 3D 虚拟商业街 Street_Empire

基于 Three.js 的可交互 3D 商业街漫游 Demo：开局选择角色，在按**青果巷真实空间序列**搭建的街区里第三人称行走，
点击店铺可查看信息、购买商品；**走到店门口光圈内按 `E` 才能进店**，进店后浏览商品并与店员对话；按 `M` 可切换到类百度地图的斜俯视总览，
看清「哪家店在什么位置、后面是什么」。支持**多人在线**：其他玩家以同款 3D 形象出现在街上，顶栏实时显示在线人数；**走近对方（4 米内）点击其角色**即可一对一私聊，也可以禁止对方给你发消息，
管理员可在 `/admin.html` 发布系统公告。

> 当前建筑与室内均为**程序化生成模型**（非实景贴图），建筑位置按公开资料近似还原；
> 真实 Blender GLB 模型接入方式见「[接入真实 GLB 模型](#接入真实-glb-模型)」。

## 快速开始

```bash
npm install      # 安装依赖（three / vite / express / ws / sql.js ...）
npm run dev      # 开发模式（前端，默认 http://localhost:5177）
npm run server   # 启动后端（默认 http://localhost:3003）
npm run build    # 生产构建，输出到 dist/
npm run preview  # 预览构建产物
```

**两个终端分别跑**：前端 Vite dev server 会把 `/api` 和 `/chat` 代理到后端 3003 端口。
后端默认使用 **SQLite**（`data/qingguo.db` + `data/messages.jsonl`），详见「后端架构」。

环境要求：Node.js 18+，浏览器需支持 WebGL 与 Pointer Lock。

## 操作说明

### 开局：选择角色

加载完成后弹出角色选择面板，点卡片开始；也可直接按 `Enter` 以默认角色（男生「阿青」）开始。
昵称输入框可自定义头顶名牌，留空则使用角色默认名。**默认昵称 = 随机词条 + 当天日期**，如「黛瓦听雨1111」（月日连写 4 位），
每次打开都会换一个不同的词条（上次词条记在 `localStorage` 的 `qingguo_last_nick`，比较时自动去掉日期后缀），
点 🎲 可继续换，也不会连续重复。词条池共 72 个，分巷弄意象 / 地标典故 / 江南雅致 / 常州风味 / 现代活泼五类。

| 角色 | 造型 | 默认名 |
| --- | --- | --- |
| 男生 | 圆润短发、蓝衬衫、深色长裤 | 阿青（默认） |
| 女生 | 圆润马尾辫、**红色连衣裙**（圆台裙摆） | 小果 |

### 街道与地图模式

| 操作 | 说明 |
| --- | --- |
| `W A S D` / 方向键 | 相对镜头方向移动 |
| 鼠标移动 | 旋转第三人称视角（点击画面锁定鼠标，`Esc` 解锁） |
| `Shift` | 冲刺奔跑（6 → 12 m/s） |
| 鼠标左键点店铺建筑 | 打开店铺信息卡片（**不进入**店内） |
| 鼠标左键点店铺上方图标 | 打开店铺信息卡片 |
| 走进店铺门口光圈并停下 | 自动弹出店铺信息卡片（**奔跑路过不打断**），同时提示「按 `E` 进入」 |
| `E` | **在光圈内进入店铺**；店内与店员交谈（靠近/瞄准交互物亦可点击） |
| `M` | **进入 / 退出地图总览模式** |
| `T` | 打开 / 关闭**资本轮回面板**（轮回 + 永久天赋树） |
| `Tab` | 打开 / 关闭**私聊面板**（Enter 发送、Shift+Enter 换行、Esc 关闭） |
| 鼠标左键点**身边的其他玩家**（4 米内） | 打开与对方的私聊；距离过远只提示「离得太远」 |
| `Esc` | 依次关闭：聊天 → 轮回面板 → 地图模式 → 店员对话 → 店铺卡片 → 退出店铺 |

**地图模式**（仿百度地图 3D 视角）：左键拖拽平移、滚轮缩放（相机高度 35–170m），
所有店铺屋顶显示名字标签；点击标签或建筑即飞到该店门口落地并自动弹出信息卡。

界面组成：顶部导航（在线人数 + 余额 + 首富榜轮播 + 护盘提醒开关）、顶栏公告条、左侧当前位置 / 家族分红 / 商业任务 / 街区商家（**全部 18 家，标题右侧显示数量，面板可滚动**）/ 探索进度、右侧店铺信息卡、底部操作提示与角色状态。

### 退出游戏

顶栏右侧「退出」按钮 → 确认弹窗（可 `Esc` 或点遮罩取消）→ 确认后显示全屏「已退出游览」页，
游戏循环停止、鼠标锁定释放；点「重新进入」刷新页面回到角色选择。

## 功能一览

- **角色选择与双角色**：开局选男（阿青，默认）/ 女（小果，红裙），可自定义昵称，头顶名牌始终朝向镜头。
- **圆润角色造型**：胶囊体四肢、球形头/手/鞋、圆台裙摆、半球头发，告别方块低模。
- **多人在线 + 房间分流**：WebSocket 同步在线列表与位置，其他玩家以同款圆润模型 + 头顶昵称牌出现在街道上（服务端 1Hz 推送、本地插值平滑）。连接 `/chat?room=N`（1–10 号房，每房 ≤30 人），顶栏「🏠 N 号房 · M/30」徽标**点击弹出房间列表**（各房人数进度条、满房禁选、全服在线数）→ 点选即切换（`chat.reconnectTo(roomId)`）；**会记住上次所在房间**（`localStorage.qingguo_room`，重开浏览器仍回原房间，满员时自动换房）；`players` 只推本房，**全服战报弹幕跨房间同步**（踢馆、收购等世界事件所有房间可见）。
- **多客户端联调**：登录凭证存在 `sessionStorage`，**每个标签页就是一个独立客户端**——开两个新标签（或两个浏览器）可分别选阿青 / 小果，各自看到对方在街上走动。刷新不掉线，关闭标签后重开需重新选角色（新会话 = 新账号、余额回到 ¥500）。若复制标签页导致沿用了同一个登录态，在地址后加 `?fresh` 即可强制换一个客户端。
- **聊天双频道 + 玩家资料卡**：**🌐 广场（全服聊天）**——跨房间广播、3s 限频、dnd 禁言、内存暂存最近 50 条；**💬 私聊**——Tab 面板内切换，在线列表点选不限距离与场景发起；消息增量追加 + 智能滚动。**玩家资料卡**——广场消息昵称 / 在线列表「👤」按钮点开，展示昵称、称号、店铺总身价、累计收益、每秒收租、轮回次数与名下店铺列表（不含现金余额）。
- **系统公告**：管理员在 `/admin.html` 发布，玩家顶栏公告条展示最新一条启用中的公告。
- **普通店铺保护期 + 新手安全期**：普通档店铺（¥50–500 万）易主后 4 小时内不可再被踢馆；店主注册 ≤4 小时或总资产 ≤1000 万时，其名下普通店同样免疫（精品 / 黄金不保护，两档照常争夺）。
- **首富榜 / 断线补拉 / 后台通知**：顶栏 🏆 首富榜 30s 刷新、4s 轮播前三；WS 重连后自动补拉 state 恢复护盘弹窗；页面在后台时护盘提醒叠加本地系统通知与标题闪烁。
- **真实街区布局**：按青果巷公开资料的东→西序列布置建筑、支巷与河道，见「[真实布局数据](#2-真实布局数据化)」。
- **第三人称漫游**：Pointer Lock 鼠标视角、WASD 相对移动、Shift 冲刺、跳跃与重力贴地。
- **碰撞与边界**：基于 `THREE.Box3` 的 AABB 分轴碰撞，建筑不可穿过，角色不可走出地图。
- **地图总览模式**：`M` 切换斜俯视，拖拽平移、滚轮缩放、屋顶店名标签、点击飞过去。
- **店铺三层交互**
  1. 地面发光触发圈（半径 1.5m）：走进去并**停下脚步**时自动弹卡（跑过不打断移动），圈体随玩家靠近变绿并呼吸；**在圈内按 `E` 才能进店**。
  2. 店铺上方浮动图标（Sprite）：始终面向镜头，`depthTest:false` 不会被建筑遮挡。
  3. 店铺建筑本体：点击只打开信息卡片，不再直接进店。
- **进店 / 离店**：淡入淡出遮罩过渡，进出店镜头立即对齐（`snap`），不会横跨地图。
- **店内购物**：点击柜台、货架或商品，打开商品卡片购买；余额不足会提示。
- **店员对话**：每位店员有姓名、职业、问候语和多个话题，点击店员或按 `E` 打开对话面板。
- **虚拟钱包**：初始 ¥500，余额以服务端为准，购买记录按标签页写入 `sessionStorage`，个人中心可充值 / 重置。
- **退出游戏**：顶栏「退出」按钮，二次确认后进入「已退出游览」页，可重新进入。
- **开局逆袭引导（前 3 分钟）**：新账号首次进入自动播三幕剧情（势利眼店长嘲讽 → 龙王归来体验卡 → 管家送钱），可跳过；点「立即领取」走服务端 `POST /api/game/intro/grant` 一次性空投 ¥5000 万（`intro_grants` 表幂等，防反复注册刷钱），跳过则右上角留「🎁 新人体验卡待领取」胶囊随时补领。
- **护盘名场面**：护盘成功瞬间全屏喷 110 张钞票粒子（纯 DOM + CSS，不占 WebGL 帧预算）+ 金色台词，配合合成音效与全服战报弹幕；领取空投同样有钞票雨。
- **首富排面 + 膜拜红包**：全服财富榜（现金 + 店铺身价，门槛 ¥500 万）第一名易主时跨房间广播金色弹幕；首富脚下自动生成金圈 + 红毯、本人右上角出现「👑 全服首富」专属头衔框；走到首富身边点击角色弹出「💎 膜拜领红包 / 💬 私聊」菜单，膜拜得 ¥5 万（系统发放，每人每小时一次，流水写 `transaction_logs`）。
- **秘书 / 管家 HUD（右下）**：分红领取、收租暴击、护盘成功、收购/装修升级、任务领取、登顶首富时滑入一句台词（带头像 + 「叮」提示音，约 3.6 秒自动淡出）；首次触发时从 3 个人设（贴身助理 / 千金闺蜜 / 财神小仙童）里选一位，选定后不换——人设卡是**右下角小卡片，不铺全屏、不挡操作**，可点「稍后再选」（之后靠常驻的「🎭 选秘书」小入口补选）；非紧急台词每 5 分钟最多 1 条，护盘警报不受限；气泡右上角 🔔 可关掉动画与提示音（文字照常显示）。
- **光照氛围**：ACES 色调映射、PCFSoft 软阴影、程序化天空渐变、指数雾、室内分层照明。
- **加载与容错**：加载进度条、失败重试按钮、全局错误 toast、GLB 加载失败自动回退到程序化街道。
- **18 家可收购资产**：分三档（普通 7 / 精品 7 / 黄金 4，剧情按四幕展开），价格从 ¥50 万到 ¥5000 亿不等，持有后每秒自动产生租金收入，最多豪华装修 5 级。
- **资本踢馆（PvP）**：对他人店铺发起恶意收购（出价 = 资产身价 ×1.5），原店主有 15 秒窗口应对：**强力护盘**（护盘价 = 攻击出价 ×1.5，护盘成功攻击方资金作为赔偿）、**认栽**、**在线讨价还价**（每场一次，还价区间 = 出价 1.2–2.0 倍由系统约束，攻击方同意即按还价立即成交、拒绝则继续对抗）；护盘失败 / 认栽 / 超时 / 还价成交，店铺易主，**收购款全额打入原店主账户**（离线被收购也按系统价强制变现，上线即见款）。
- **5 分钟店铺保护期**：每场踢馆结束后，该店铺进入全局 5 分钟保护期（持久化到 SQLite），期间任何人无法再次发起踢馆；前端资产卡片显示倒计时并禁用按钮。
- **全服战报弹幕**：踢馆、护盘、收购、暴击、打脸等关键时刻自动推送全服战报，底部弹幕区域实时滚动。
- **街头经济闭环**
  - 金币雨：街道各处周期性掉落金币（¥2–8 万，6% 暴击 ¥50 万），450ms 冷却防刷
  - 财阀金币箱：街角大宝箱（¥80 万–200 万），45 秒冷却
  - 碰瓷 NPC：2 个势利眼角色（富二代 z=-53 / 恶毒亲戚 z=-191），打脸成功各爆 ¥2000 万，每人每 NPC 2 小时独立冷却；**已支持沿街闲逛巡逻**（以出生点为中心 ±12m 漂移，对话时站定）
  - 家族分红：离线期间按「基础 ¥6 万/小时 + 每店 ¥12 万/小时」累积，最多 8 小时，在线一键领取
- **5 个商业任务**：金币箱猎人（50 万）、打脸名场面（100 万）、百步穿街（30 万）、护盘大鳄（150 万）、野蛮收购（300 万），进度由服务端事件自动累加，达成后可一次性领取。
- **财富称号进化**：按持有店铺数量自动升级称号（街头路人甲 → 保安克星 → 街区包租公 → 千亿财阀 → 千亿商业教父 → 全球经济唯一的爹），远端玩家头顶气泡显示「昵称 + 称号」双行。
- **资本轮回（Prestige）**：持有资产总身价 ≥ 500 亿（约等于买下一家黄金店）可清零重生——现金与店铺归零，按「每 5 亿身价 = 1 张传世黑卡」换点数（刚好过线 100 张，全收集约 2,028 张，满级盘约 10,270 张），开启新一轮制霸；轮回次数与点数永久累积。
- **永久天赋树**：3 棵天赋各 5 级，黑卡点数点亮、轮回不清除——点金手（金币雨暴击率 6%→26%、暴击奖励 +30%/级）、资本压制（收购 / 装修价每级 −6%，满级 7 折，不影响踢馆出价）、躺平收租（家族分红速率每级 +20%，满级 ×2）。`T` 键打开面板。

## 核心设计

### 1. 建筑模型与商铺数据分离

- 场景中的建筑只负责**几何与位置**，通过 `mesh.userData.shopId` 声明「我是哪家店」。
- 名称、分类、简介、营业时间、商品、价格全部在 `src/data/shops.js`。
- 室内配色在 `src/data/interiors.js`，店员与对话内容在 `src/data/npcs.js`。
- 换模型、改商品、加话题互不影响，新增一家店只需：模型命名 `shop_<id>` + 在 `shops.js` 增加同 `id` 的数据。

### 2. 真实布局数据化

`src/data/layout.js` 用坐标把青果巷的空间关系描述出来，`ProceduralStreet.js` 只负责按数据生成几何，
**位置与造型互不影响**，以后改点位不用碰建模代码。

- **坐标系**：`z = 0` 为东入口牌坊，往西 `z` 递减（`z = -494` 为西入口）；`+x` 为巷北，`-x` 为巷南。
- **街道参数**（`STREET`）：巷宽 9m、行走边界 `x ∈ [-3.9, 3.9]`、`z ∈ [-491, 11]`；南市河在巷南 `x = -25 ~ -44`。
- **支巷**（`LANES`）：正素巷 `z = -88`、天井巷 `z = -300`、雪洞巷 `z = -365`，均向北延伸约 30–34m。
- **建筑**（`BUILDINGS`，约 55 条）：`w` 临街面宽（沿 z）、`d` 进深（沿 x，30–55m）、`h` 檐口高。

**立面生成规则**：临街立面按 3.4m 开间排布门窗（门居中、其余为窗，两层建筑加二层窗）；
进深超过 8m 的深宅屋顶按「进」分段起脊，避免出现十几米长的巨型屋面；
白墙与黛瓦各有 3–4 档色差，相邻建筑不同色。

### 3. 同场景传送的室内方案

进店不切换 `Scene`，而是在街道之外的独立坐标区（`x = 600 + n × 40`）为每家店生成一个
14m × 14m 的室内房间：

- **懒构建**：首次进入时才生成，避免拖慢首屏；生成后缓存，再次进入复用。
- **可见性切换**：同一时刻只显示当前房间。
- **碰撞体切换**：进入时把 `Player` 的 colliders / bounds / groundY 换成室内的，离店时还原。
- **遮罩过渡**：`#scene-fade` 淡出 → 切换 → 淡入，掩盖传送瞬间。
- **天花板**：平面旋转 90° 且正面朝下，只从室内可见；从上方俯视被背面剔除，不会挡住第三人称相机。

### 4. 点击进店与拾取兜底

第三人称相机始终略微俯视角色，准星实际落在角色身后的地面上，直接使用屏幕中心射线常常打不到建筑。
因此 `ShopInteraction._pickShop()` 采用两级拾取：

1. 先按鼠标位置 / 屏幕中心（鼠标锁定时）发射射线；
2. 未命中时，沿摄像机**水平朝前**方向再射一次，保证「站在店前、看向店铺、点一下」就能打开店铺信息卡片。

命中建筑或头顶图标 → 打开信息卡片。进店必须走进门口触发圈后按 `E`，点击无法直接进店。

因为一栋建筑由台基、墙身、屋顶、门窗等多个构件组成，拾取使用**递归射线**（`intersectObjects(..., true)`），
命中任意构件后沿 `parent` 链向上查找 `userData.shopId` 来判定属于哪家店。

### 5. 相机模式

| 参数 | 街道 | 室内 | 地图总览 |
| --- | --- | --- | --- |
| 跟随距离 | 6.5 | 3.2 | —（自由相机） |
| 高度 | 1.6 | 0.3 | 35 ~ 170（滚轮） |
| pitch 范围 | -0.4 ~ 1.2（默认 0.16） | -0.3 ~ 0.18 | 固定斜俯视 |

室内压低镜头并限制俯仰上限，避免相机越过 3.4m 墙顶看到「盒子外部」。
街道默认俯角从 0.3 降到 0.16，出生时能看到牌坊与两侧街景而不是只有地面。
进出店通过 `snap()` 立即对齐，避免相机从街道平滑飞到 600 米外的房间。

### 6. 角色系统

- **程序化双角色**：`Player._buildMesh(variant)` 用 `CapsuleGeometry` / `SphereGeometry` / `CylinderGeometry`
  拼出**圆润造型**，不依赖任何外部模型文件，零加载开销。
  - 通用：躯干 / 四肢为胶囊体（躯干前后压扁），球形头 + 球形手 + 压扁球形圆头鞋，头顶半球发罩。
  - 男生：后脑短发（压扁球体贴在脑后）+ 蓝衬衫 + 深色长裤。
  - 女生：长发后披 + 两侧鬓发 + 马尾（均为胶囊体）+ **红色连衣裙**（上窄下宽的圆台裙摆，裙下露小腿）。
- **骨架式摆动**：四肢挂在髋部 / 肩部的 pivot `Group` 上，行走时 `rotation.x` 按相位正弦摆动，
  奔跑相位更快（9 → 13 rad/s），静止时按 `dt` 插值平滑回正。
- **头顶名牌**：`CanvasTexture` + `Sprite`（`depthTest: false`），显示角色昵称，始终朝向相机。
- **模型与碰撞解耦**：模型 `rig` 原点下移半高，使 `Group` 原点仍在碰撞体中心，移动 / 碰撞 / 传送逻辑完全不变。

### 7. 地图总览模式

`MapView.js` 复用同一个 `camera` 与 `scene`，不新建场景：

- **进入**：0.9s 补间从当前位姿飞到俯瞰位姿，同时把雾密度从 0.007 降到 0.0016、`camera.far` 拉到 1200，
  保证 500m 长的巷子能看清。
- **平移 / 缩放**：左键拖拽按相机高度换算地面位移；滚轮改变高度 35–170m，中心点钳制在街区范围内。
- **店名标签**：每家店在屋顶上方 2.2m 生成一个 `Sprite`，进入地图才显示。
- **点击飞行**：先拾取标签、再拾取建筑本体，命中后 1.1s 飞到店铺门口上空，再传送玩家并切回第三人称，
  玩家落在门口触发圈内，信息卡自动弹出。
- **输入隔离**：地图模式期间 `tpCamera.enabled = false`、`interaction.enabled = false`，
  避免点击被指针锁或店铺交互抢走。

### 8. 移动与碰撞

- 角色用 AABB（`Box3` + 半径 0.5 / 身高 1.8）做 X、Z 分轴检测，撞墙时按轴回退。
- 重力贴地，`groundY` 由场景（或室内房间）提供。
- `bounds` 钳制角色中心，保证不走出地图（街道 `x ∈ [-3.9, 3.9]`，`z ∈ [-491, 11]`）。

### 9. 钱包与购买

- `wallet.subscribe()` 订阅式刷新顶栏余额，注册时立即回调一次。
- `wallet.buy(productId, price, name, qty, api)` 走 `/api/orders` 事务扣余额，成功累加购买数量。
- 余额以后端为准；购买记录写入 `sessionStorage`（key：`qingguo_wallet_v1`），刷新不丢失；个人中心支持充值 / 重置为 ¥500。

### 10. 后端架构（SQLite + 预留 MySQL 升级路径）

后端入口：`server/index.js`，与 Express 共享一个 HTTP 端口（3003），WebSocket 挂在 `/chat` 子路径。

**数据库选型与升级**：

当前用 **SQLite**（sql.js WASM 版本）——零编译、零配置、`npm i` 就能跑，数据就是一个文件 `data/qingguo.db`。
本项目的数据体量（用户几百、商铺几十、消息千级）在 SQLite 下性能**比 MySQL 还快**（没有网络层和服务进程开销）。

但如果未来上多人在线且需要多进程部署，**可以无损升级到 MySQL**，理由：

1. **SQL 方言完全兼容**：所有 SQL 都是 ANSI 标准写法（`TEXT / INTEGER / REAL`、`INSERT INTO ?`、`CREATE TABLE IF NOT EXISTS`），没有 SQLite 专属语法（如 `INSERT OR REPLACE`、`AUTOINCREMENT`）
2. **统一 API 层**：`server/db.js` 导出的 `run(sql, params)` / `query(sql, params)` 是唯一的数据访问入口，上层 auth.js / chat.js / index.js **一行都不用改**
3. **升级脚本已备**：`node server/migrate-to-mysql.js` 自动建库、建表、逐表 upsert 迁移
4. **切换开关明确**：只认 `USE_MYSQL=true` 这一个显式环境变量（经验告诫：不要用"是否存在 MYSQL_HOST"等隐式条件）

**聊天消息历史**单独用 **JSONL 追加写入**（`data/messages.jsonl`），与数据库解耦——
每行一条、O(1) 追加、进程崩溃也不会损坏历史，这个方案在 MySQL 模式下继续原样使用。

**WebSocket 协议**（JSON envelope：`{ type, payload }`）：

| type | 方向 | payload | 说明 |
| --- | --- | --- | --- |
| hello | C→S | `{ token }` | 鉴权握手 |
| position | C→S | `{ x, z, yaw }` | 位置上报（每 2s，用于在线列表） |
| dm | C→S / S→C | `{ to, text }` / `{ from, to, text, ts }` | **私聊**：只发给发送方与接收方 |

### 11.5 多房间分流 × 全服统一世界状态（架构决策）

**核心命题**：当在线玩家超过 60–80 人时，单一 WebSocket 广播 `players` 列表和实时 battle 消息会让前端性能雪崩（每帧 60 个 Sprite 渲染 + DOM 弹幕 × N）。因此**街道场景允许拆成多个分流房间**（Instance / Shard），但**世界状态（资产归属、踢馆冷却、NPC 刷新、金币宝箱位置）在全服层面只存一份**。

#### 3 号房间 30 人 vs 5 号房间 30 人

```
           ┌───────────────────────────────────────────────────┐
           │                  世界状态层（全局唯一）              │
           │  shops.id ──► ownerId / cooldownMs / level / income│
           │  attacks.status ──► pending → resolved → expired   │
           │  coins / boxes / npc_claims / battle_logs          │
           │  ───────── SQLite / 单后端进程 / 无复制 ─────────  │
           └──────────┬──────────────────────┬─────────────────┘
                      │                      │
           ┌──────────▼──────────┐  ┌────────▼────────┐
           │ 房间 3 (30 人)       │  │ 房间 5 (30 人)    │
           │ /chat?room=3         │  │ /chat?room=5     │
           │ 每秒 broadcast 30人   │  │ 每秒 broadcast 30人│
           │ battle 弹幕跨房间接收 │  │ battle 弹幕跨房间接收│
           └──────────┬──────────┘  └────────┬─────────┘
                      │                      │
           ┌──────────▼──────────┐  ┌────────▼─────────┐
           │  3D 场景副本         │  │  3D 场景副本       │
           │  同一套 layout.js    │  │  同一套 layout.js  │
           │  程序化生成同一地形   │  │  程序化生成同一地形  │
           │  AssetVisuals 同步    │  │  AssetVisuals 同步 │
           └──────────────────────┘  └─────────────────┘
```

#### 四层不变量（必须严格遵守）

| # | 不变量 | 保证方式 |
| --- | --- | --- |
| ① | **店铺不因为房间不同而复制** | `shops` 表按 `shopId` 主键，全服唯一；任何房间发起的 `/api/game/attack { assetId: 'cafe' }` 都落到同一条 `shop_attacks` 记录上 |
| ② | **玩家看到的店铺归属全部一致** | `GET /api/game/state` 返回的 `assets[]` 不包含"房间号"字段；`cooldownMs`、`ownerNick`、`attacking` 均从全局 world 读取 |
| ③ | **踢馆竞争由全服统一结算** | `capital.js` 里的"同时只允许一场 pending 踢馆"用内存 `pending` Map + DB 行锁双重保证；房间 A 发起 attack，房间 B 同一店铺的 attack 会立即收到 `{"error": "这家店正在被争夺中"}` |
| ④ | **房间之间不隔离世界事件** | `broadcastBattle()` 不走"只广播本房间"的逻辑；所有在线玩家（无论在哪个 `/chat?room=N`）都收到 battle WS 消息 → Danmaku 弹幕跨房间显示 |

#### 玩家可感知的结果

> **例如**：3 号房间有 30 人正在逛街，5 号房间也有 30 人正在逛街，他们都看到「街角咖啡」挂在 `pcA92486` 名下保护期 2 分钟。3 号房间的土豪对它发起踢馆，**5 号房间的所有人也会在 Danmaku 弹幕里看到**：
> `💥 土豪 对「街角咖啡」发起踢馆，出价 ¥180 万！`
> 5 号房间的 `pcA92486` 自己也会收到 `shop_attack` WS 警报 + 弹出 AttackAlert 全屏警告。
> 等 15s 超时，**两个房间同时收到 `shop_attack_result`** 和结算弹幕，保护期延长到 5 分钟，两个房间的 AssetCard 圆环同步走完。

#### 实现要点（已全部落地）

| 模块 | 设计 | 实现状态 |
| --- | --- | --- |
| WebSocket 连接 | `/chat?room=<id>` 参数化；`chat.js` 维护 `rooms: Map<roomId, Set<ws>>` | ✅ 已实现（`parseRoom` 从 URL 解析，1–10 房，空房间自动释放） |
| `players` 推送 | 改为按房间广播各自在线玩家列表；跨房间的 battle 消息 **仍广播所有房间** | ✅ 已实现（每秒 tick 按 `rooms` 逐房广播；`buildNearbyList(roomId)` 房间内过滤） |
| `broadcastBattle()` | 已走 `for (const ws of allSockets)` | ✅ 保持不变（全局广播保证弹幕跨房间同步，集成测试已验证） |
| `/api/game/state` | 无 `roomId` 字段 | ✅ 保持不变（状态查询就是全局世界视角） |
| `capital.js` 冷却持久化 | `shop_cooldowns` 表按 `shopId` 全局唯一 | ✅ 保持不变（冷却不感知房间） |

| **房间容量** | 每房 ≤30 人（按去重在线用户计，同一用户多连接算 1 人） | ✅ 已实现（`ROOM_CAPACITY`，hello 阶段校验，满房返回 `room-full` error 并关闭） |

#### 为什么不用"一房间一独立世界"？

| 方案 | 优点 | 致命缺点 |
| --- | --- | --- |
| **每个房间一独立世界**（房间 3 的 cafe ≠ 房间 5 的 cafe） | 物理上隔离，玩家不会互相干扰 | 💀 没有 PvP：你在 3 号房抢的 cafe，5 号房的人看不到 → 资产争夺就失效了；💀 老板要在每个房间各自买一份；💀 battle_logs 碎片化，全服战报失去意义 |
| **多房间场景 × 全局世界**（✅ 采用） | 物理分流保护性能，PvP 争夺保持全服尺度 | 实现略复杂（WS 需要同时支持"房间内 players 推送"和"全局 battle 广播"两种模式） |

结论：**性能瓶颈在 `players` 广播量，不在世界状态数据量**——一份 shops 表（18 行）+ 一份 cooldowns 表（≤ 18 行）+ 一份 pending attacks 表（≤ 18 行）放在 SQLite 里毫无压力；真正要拆的是"同时有多少个玩家 position 被每秒推送"。所以多房间只用来分流 players 广播，世界状态绝不复制。

#### 当前实现与大规模并发的扩展方式（世界分片）

**当前实现**：房间分流（`/chat?room=N`，1–10 号房、每房 ≤30 人）**已落地**——只分流 `players` 位置广播，battle / top1 仍全局广播；店铺全服唯一、任何情况下都不会因为房间不同而重复（不可重复购买）。**世界分片尚未做**（当前仍是单库单世界）：

**未来在线规模上来（例如单服几百人）时，正确的扩展顺序**：

| 层 | 做法 | 解决什么 | 代价 |
| --- | --- | --- | --- |
| 房间（room）✅ 已实现 | `/chat?room=N` 只分流**玩家位置广播**，每房 ≤30 人；世界状态、战报、榜单仍全服一份 | 渲染/带宽压力 | 无明显玩法代价 |
| **世界分片（sharding）** | 每 30–50 人一份**独立数据库/经济世界**，每个分片各有一套 18 家店——跨分片店铺"重复"，分片内仍然唯一 | 几百人抢 18 家店的稀缺度过高 | 首富榜要按分片出或做合并榜；跨分片不能一起逛街/互相踢馆；登录时需选分片或自动分配 |

> 注意区分：**"按房间复制店铺"是错误设计**（会摧毁跨房 PvP 和全服战报的意义）；
> **"按世界分片复制经济"是正确扩容方式**（每个分片是一个完整的、内部自洽的小世界）。
> 简言之：房间分人，分片分世界；房间共享同一套店铺，分片之间各自一套。

### 11.6 商业街分层设计与赚钱路径多样性

商业街不能只有"抢店铺"一种玩法——那会导致所有资金流向集中在最贵的几家，新人毫无生存空间。**必须设计三档店铺稀缺度 + 至少三条赚钱路径**：

#### 三档店铺稀缺度

```
稀缺度          数量        价格段              竞争强度     玩家目标层
─────────────────────────────────────────────────────────────────────
🏪 普通店铺     7 家        ¥50 万 – ¥500 万     低          新人 / 小老板
              稳定经营机会，回本 100–200 秒
              典型：奶茶铺、馄饨铺、咖啡店、茶肆、面包房、糖水铺、花坊

✨ 精品店铺     7 家        ¥2,000 万 – ¥100 亿   中高        资本玩家 / 连锁主
              需要一定资金积累，回本 ~3 分钟
              典型：书店、数码城、城隍庙戏楼、文化记忆馆、松健堂、赵元任故居、恽鸿仪可园

👑 黄金店铺     4 家        ¥500 亿 – ¥5000 亿    全服争夺     顶级财阀 / 首富榜
              持有即登顶，踢馆最激烈，保护期最常被刷新
              典型：八桂堂总部、半园庄园、礼和堂会所、西入口金融中心
```

**稀缺度数量是全服总量，不是每房间一份**：

> ❌ 错误设计：如果有 10 个房间，每个房间复制 20 家店铺 → 200 家店 × 每个玩家持 2 家 → 所有人都能当老板 → 竞争消失。
>
> ✅ 正确设计：全服只放 18 家核心可收购资产（4 黄金 + 7 精品 + 7 普通），分布在唯一的青果巷 layout 上。所有房间（3 号房、5 号房、10 号房...）共享这 18 家店的所有权。3 号房的土豪抢了 cafe，5 号房的老板就失去 cafe——竞争才真实存在。

#### 房间规模：每房间 30 人

| 指标 | 数值 | 理由 |
| --- | --- | --- |
| 每房间人数上限 | **30 人** | Three.js 每帧最多稳定渲染 ~30 个远端玩家 Sprite（含阴影 / 头顶气泡 / 走路动画）。超过 30 人单房间会掉帧 + 弹幕滚动肉眼跟不上 |
| 房间数 | 动态伸缩，单后端支撑 ≤ 10 个房间 | 10 房间 × 30 人 = 300 同时在线，对 SQLite + 单 Node 进程的世界状态层毫无压力 |
| 分流策略 | 玩家首次进入自动分配到最空的房间；提供手动切换入口（`/room=N`） | 避免一个房间扎堆；老板找老板踢馆时可以跨房间找朋友观战 |

#### 赚钱路径：至少三条并行

| --- | --- | --- | --- |

| **② 踢馆掠夺** | 资本玩家 | 出价 1.5× 身价抢他人店铺 | ✅ 已实现 |

| **⑦ 街头经济** | 路人 / 急需现金者 | 金币雨 ¥2–8 万、宝箱 ¥80 万–200 万、碰瓷 NPC ¥2000 万 | ✅ 已实现 |

#### "不抢店铺也能活"的兜底设计

普通玩家如果暂时买不起 50 万的奶茶铺（刚注册只有 50 万启动金），他依然可以：

1. **碰瓷 NPC 暴富**（打富二代 + 恶毒亲戚各一次 = ¥4000 万）
2. **捡金币箱**（一个 ¥800–2000 万，45 秒冷却）
3. **进店内消费体验**（不一定要成为店主，做消费者也能感受街道氛围）
4. **做任务攒钱**（5 任务最高 ¥510 万）

> 目标：**玩家不需要被迫在"抢店铺"和"滚蛋"之间二选一**。街头经济闭环让即使完全不碰 PvP 的路人也有可玩内容。

### 11.7 普通店铺保护期 + 防恶意脚本（Anti-Cheat & Protection）

#### 普通店铺保护期（Tier-1 Grace Period）

**设计原则**：游戏是娱乐，玩家不会全天守店。普通店铺的保护由**两条独立规则**构成，
满足任一即免疫踢馆——老玩家开小号收割新人的路被彻底堵死，同时也不给大号靠"卖光资产装新手"留后门。

```
规则 A（按店铺）：店铺易主（收购 / 被踢馆后易主）后 4 小时内不可被踢馆
规则 B（按账号）：店主人处于新手安全期 —— 注册 ≤ 4 小时 或 总资产（现金+店铺身价）≤ 1000 万

保护范围：
  ✅ 普通店铺（¥50 万 – ¥500 万 tier 1）
  ❌ 精品 / 黄金店铺不保护
  ❌ 玩家不能利用保护期"主动发起踢馆"当挡箭牌（攻击方仍走正常规则）

实现：
  player_shops.acquired_at 记录易主时间 → tier1Protection(shopId)
  users.created_at + balance + player_shops 身价 → isNewPlayer(userId)
  capital.createAttack() 入口依次检查两条规则，命中任一 → 409
    「这家普通店铺刚易主，还在保护期内（约剩 X 小时），暂不可踢馆」
    「这家普通店铺受新手保护：对方注册不足 4 小时 / 对方总资产不足 1000 万，暂不可踢馆」

UI 表现：
  他人视角 → AssetCard 显示「🛡 刚易主 · 保护期内无法踢馆」/「🛡 新手保护期 · 无法踢馆」并禁用踢馆按钮
```

> **实现状态**：`server/capital.js` 的 `tier1Protection()`、`isNewPlayer()` + `createAttack()` 入口拦截（命中返回 409）；
> `server/game.js` 的 `buildState()` 下发 `ownerProtected` / `ownerProtectedHours` / `ownerProtectedReason`（`transfer` | `register` | `assets`）。
> 常量 `TIER1_PROTECT_HOURS = 4`、`NEWBIE_AGE_MS = 4h`、`NEWBIE_ASSET_CAP = 1000 万`。

**为什么只保护普通店铺？**

| 档位 | 保护 | 理由 |
| --- | --- | --- |
| 🏪 普通（¥50–500 万） | ✅ 保护 | 这是新人攒第一桶金的主要场景——奶茶铺 / 面包房 / 花坊 回本 100–200 秒，刚买 1 分钟就被大号踢走 → 新人直接弃坑 |
| ✨ 精品（¥2000 万–100 亿） | ❌ 不保护 | 买得起精品的玩家本身已不是纯新手；精品是资本玩家争夺的核心区域，不保护才能制造全服焦点战 |
| 👑 黄金（¥500 亿+） | ❌ 不保护 | 持有黄金店的玩家本身就是 Top 梯队，被踢是正常竞争；保护黄金店会让顶层失去流通 |

**反小号刷保护期对策**：

| 作弊场景 | 检测手段 |
| --- | --- |
| 大号 A 踢自己小号 B 的店 | `capital.createAttack()` 入口已拦截 `if (attackerId === defenderId)` |
| 多个小号在同一 IP 互相踢 | 记录 `(ip, shopId, attack_count_in_1h)`；> 3 次 → 自动加额外保护期 + 人工审核 |
| 小号买普通店 → 保护自动失效 → 被大号秒踢 | 保护期从**每次易主**起算 4 小时，与账号是否小号无关；4 小时后即恢复正常竞争 |
| 大号把资产卖给小号，让店铺落进新手保护 | 规则 B 是「注册 ≤4h **或** 总资产 ≤1000 万」，二者任一成立即保护；大号转店后若总资产仍 >1000 万则不触发，且转店本身走正常收购计价 |
| 小号持有多店触发保护期叠加 | 规则 A 按**店铺**判定，各家店只享受自己易主后的 4 小时；规则 B 按**账号**判定，不因持有多店而叠加 |

#### 权威后端防作弊（Server-Authoritative）

**核心原则：前端只负责"表现"，所有数值计算必须在服务端完成**。修改本地 JS 内存、改 fetch 参数、甚至 hook 掉 WebSocket 消息处理器，都不能产生真实收益。

**五件绝对不能信任前端的事**：

| 禁止信任 | 当前实现 | 为什么必须后端算 |
| --- | --- | --- |
| **金币产出金额**（捡金币 / 宝箱） | ✅ 后端 `treasure.collect()` 内 `randomInt(20000, 80000)` | 前端就算传 `{ type: 'coin', amount: 1e12 }` 也被忽略；返回的是服务端生成的随机数 |
| **收租结算**（每秒自动累加） | ✅ 后端 `economy.settle(userId)` 惰性按 `Date.now()` 算 | 前端就算把 `gameStore.user.incomePerSec` 改大，`GET /api/game/state` 返回的永远是服务端余额 |
| **收购扣款**（`/api/game/acquire`） | ✅ 后端 `UPDATE users SET balance = balance - price WHERE id = ? AND balance >= price` | 前端传任何虚假的 `price` 都不参与结算；只查 DB 余额够不够 |
| **踢馆出价 / 护盘费** | ✅ 后端 `attackBidOf(asset, level)` + `defendCost = bid * 1.5` | 前端就算传 `/api/game/attack { bid: 1 }` 也按服务端算的值扣款 |
| **冷却时间 / 保护期剩余** | ✅ 后端 `shop_cooldowns` 表存 `cool_until INTEGER` | 前端就算把 AssetCard 冷却圆环改回 0，`cooldownMs` 永远由服务端 state 返回 |

**四件可以信任前端的事**（非数值性、不影响结算）：

| 可信任 | 说明 |
| --- | --- |
| 角色位置 `{ x, z, yaw }` | 只用来渲染远端玩家，不参与任何数值计算；被拉黑的玩家位置直接丢弃 |
| 走路距离 `{ meters }` | 触发任务计数，但 `questProgress()` 后端自己算累加，单次上报超过 300m 会被截断 |
| 拾取时机（什么时候点 coin） | 触发冷却计时器 `last_coin_at = now`，金额后端决定 |
| 视觉表现 | 3D 穹顶光环、SVG 圆环、飘字——这些全是视觉，服务端不在乎 |

**前端常见作弊手段 & 服务端怎么挡**：

| 作弊手段 | 危害 | 服务端拦截点 |
| --- | --- | --- |
| Chrome DevTools 改 `gameStore.user.balance = 999e9` | 前端显示 999 亿，但 API 一调用就崩 | 每次 `/api/game/state` 返回真实 `balance`，前端只是"显示真实值" |
| fetch `/api/game/acquire` 时 body 里放虚假 `price` | 0 元收购豪宅？ | 后端**忽略**请求体里的 price，直接 `findAsset(id).price` |
| WebSocket `shop_attack_result` 消息篡改 | 让前端显示"护盘成功"但实际已丢店？ | 前端必须以**下一次 `/api/game/state`** 为准；WS 消息只是通知"有变化"，不是最终真相 |
| 用 Python + requests 绕过冷却窗口狂刷 `/api/game/collect` | 绕过 450ms 冷却 | 后端 `last_coin_at` 存 DB，每次 collect 前检查 `now - last_coin_at >= 450ms`，不走 setInterval |
| 开两个浏览器 / 两个 tab 同时发起同一店 attack | 抢在 DB 锁前落两次 | DB `INSERT` 检查 `status != 'pending'` + SQLite 单写天然串行（见 §12 并发安全） |
| 改 `/api/game/quests/walked` 传 `{ meters: 9999999 }` | 一次完成 2000m 任务 | 后端 `Math.min(delta, 300)` 截断单次，再 `Math.min(progress + delta, goal)` 封顶；累计到 goal 后 `questsFor()` 返回 `done: true`，不再累加 |

### 12. 资本踢馆（PvP 争夺商铺）

`server/capital.js` + `server/game.js` + `shared/assets.js`。

**规则流程**：

```
攻击方 A ──出价(身价×1.5)──▶ 扣款托管 ──推送 shop_attack 警报──▶ 防守方 B
                                                                    │
                                                     15s 内强力护盘？│
                                                     ┌──是────────┴──否/超时──┐
                                                     ▼                           ▼
                                             B 扣护盘费(出价×1.5)           店铺直接易主
                                             A 的托管金赔偿给 B             A 的出价不予退还
                                             店铺 5min 保护期               B 付 10% 违约金
```

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 攻击出价 | `assetValue(asset, level) × 1.5` | 即时扣款托管 |
| 护盘窗口 | **15 秒** | 逾期自动判负 |
| 护盘费用 | `bid × 1.5` | 原店主支付，攻击方托管金全额赔偿给防守方 |
| 违约金 | `assetValue × 0.1` | 防守失败时从原店主余额扣（余额不足则扣到 0） |
| 保护期 | **5 分钟 / 店铺** | 持久化到 SQLite `shop_cooldowns` 表，期间任何人无法再次攻击 |

**关键实现细节**：

- **冷却持久化**：`shop_cooldowns(shopId)` / `setShopCooldown(shopId, until)` 从 SQLite 读写，到期记录自动 DELETE；每次 `createAttack()` 首先检查冷却，返回剩余秒数。
- **进程重启容错**：`initCapital()` 在服务启动时将所有 `status='pending'` 的踢馆标记为 `expired`，并清理所有过期冷却。
- **同时限制**：同一店铺同一时刻只有一场踢馆（内存 `pending` Map 互斥）。
- **推送机制**：`sendToUser(defenderId, { type: 'shop_attack', ... })` 直接 websocket 私聊原店主；结算时双方推送 `shop_attack_result`，同时 `broadcastBattle()` 全服战报。

**保护期视觉演出（前端 AssetVisuals + AssetCard）**：

服务端返回 `cooldownMs > 0` 时，双层联动：

```
  Canvas 倒计时 Sprite（每秒刷新）       UI 面板 SVG 圆环
  "🛡 保护中 4:59" + 进度弧              ┌────────────────────┐
    ↑                                   │ ◐ 4:59  🛡       │
  ┌─────────────────────┐               │ 店铺正在保护期内  │
  │  Top Cap（淡蓝盖）    │               │ 5分钟内无法发起  │
  │  Rim Torus（上沿光圈）│               │ 踢馆              │
  │                     │               └────────────────────┘
  │  Dome Cylinder      │                stroke-dashoffset 数学：
  │  （半透明蓝穹顶）     │                圆 r=20 → 周长 125.66
  │  呼吸脉冲 + 慢自转   │                offset = 125.66 × (1−progress)
  │                     │
  ├── Ring（地面光圈）  │                本地定时 vs 服务端 cooldownMs：
  │   Glow（宽底光）     │                首次 apply() 缓存 expireAt=now+cooldownMs
  └─────────────────────┘                后续 update(dt) 本地倒计时，不依赖 state 刷新
```

| 层 | 文件 | 实现 |
| --- | --- | --- |
| 3D 穹顶 | `src/scene/AssetVisuals.js` | `apply()` 检测 `cooldownMs > 0` → `_buildAura()` 建 `CylinderGeometry` + `RingGeometry` + `TorusGeometry` + Canvas 倒计时 Sprite；`update(dt)` 每帧呼吸脉冲（`sin(time*3.5)`）+ 穹顶自转（`rotation.y += dt*0.2`）+ 每秒刷新倒计时 Canvas |
| UI 面板 | `src/ui/AssetCard.js` | 进入他人被冷却店铺时启动 `_cooldownTimer`（setInterval 1s）→ `_tickCooldown()` 更新 SVG 圆环 `strokeDashoffset` + mm:ss 倒计时 + status 栏文案；到期自动清理 |
| 样式 | `src/style.css` | `.asset-cooldown` 冰蓝胶囊 + drop-shadow 发光 |
| DOM | `index.html` | asset-card 内嵌 SVG `<circle>`（track + bar） + countdown div + tip 文案 |

**客户端本地 vs 服务端时间**：首次检测到冷却时保存 `expireAt = Date.now() + cooldownMs`，后续 `apply()` 不再覆盖此值——避免服务端 state 每隔几秒刷新把倒计时永远重置回 5 分钟。`update(dt)` 直接用 `Date.now() - expireAt` 算剩余时间，到期后自动从 3D 场景移除 aura Group。

**并发安全：防止多人同时踢馆同一店铺**

B 和 C 在 1ms 内同时对 `cafe` 发起踢馆——必须保证只有一笔成功落库。

当前实现使用**内存互斥 + DB 原子性**双重保险：

```
用户 B 发起 attack('cafe')     用户 C 发起 attack('cafe')
       │                                │
       ▼                                ▼
  pending.has('cafe')?            pending.has('cafe')?
       │                                │
    false ─────┐                    true ────► 拒绝：{"error": "正在被争夺中"}
       │       │
       ▼       ▼
  pending.set('cafe', attackId)   ← 同时到达，两个 Node 进程/两个事件循环都可能通过！
       │
       ▼
  INSERT INTO shop_attacks ...
  WHERE status != 'pending' AND shop_id != 'cafe'  ← SQLite 单写，天然串行
       │
       ▼
  第二次 INSERT：UNIQUE 冲突 / status 检查失败 → 回滚
```

| 层 | 当前实现 | 高并发补齐 |
| --- | --- | --- |
| 内存锁 | `capital.pending: Map<shopId, attackId>` 单进程内有效 | 换 Redis 分布式锁（`SET shop:lock:cafe token NX PX 5000`），支持多后端水平扩展 |
| DB 原子性 | SQLite 单写天然串行；`INSERT` 前检查 `status != 'pending' AND shop_id = ?` | 迁移 MySQL 后加 `FOR UPDATE SKIP LOCKED` 行锁，避免锁等待 |
| 扣款原子性 | 余额在 `createAttack()` 入口处 `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?` | 必须用单事务（`BEGIN ... UPDATE users ... INSERT shop_attacks ... COMMIT`），防止扣款成功但踢馆记录未落库 |
| 抢店铺竞态 | 收购 `acquire` 走 `UPDATE shops SET owner_id = ? WHERE id = ? AND owner_id IS NULL` | 同样需要事务 + 乐观锁 `updated_at` 字段检查 |

> **关键教训**：Node 的单事件循环不等于"天然串行"——如果未来把后端拆成多个进程或用 PM2 cluster，内存 `pending` Map 就会失效。**所有竞争最终必须落 DB 行级原子性**，内存锁只是快路径优化。

### 12.5 在线议价收购（Counter Offer）✅ 已实现

踢馆警报弹出后，**防守方每场有一次还价机会**，把单方抢夺升级为一场谈判博弈：

```
攻击方发起踢馆（bid = 身价 ×1.5，资金托管）
        │
        ▼
防守方 AttackAlert（15 秒窗口）──┬── 强力护盘（defendCost = bid ×1.5，成功则攻击方资金作赔偿）
                                ├── 认栽离场
                                └── 💬 讨价还价（每场一次）
                                      │  滑条开价 ∈ [bid×1.2, bid×2.0]（服务端强制约束）
                                      ▼
攻击方 AttackAlert 切换攻击视角：「对方还价 ¥X」──┬── ✅ 同意：补差价（X − bid）→ 立即按 X 成交
        （主倒计时不暂停，须在剩余时间内应价）        └── ❌ 拒绝：还价作废（机会已用），照常对抗
                                        │
                              倒计时到点未应价 → 按原出价成交
```

| 层 | 文件 | 实现 |
| --- | --- | --- |
| 结算 | `server/capital.js` | `counterOffer()`（幅度/一次机会校验）+ `counterReply()`（同意：补差价 + `resolveCapture(id, 'countered', price)` 参数化结算；拒绝：counter 清空照常对抗）；`resolveCapture` 三种成交文案（认栽/离线/还价） |
| WS 路由 | `server/chat.js` | `counter_offer` / `counter_reply` 两个 case，错误回 `error`（code: counter-error） |
| WS 消息 | — | `counter_pending`（→攻击方）· `counter_ack`（还价回执）· `counter_rejected` · `counter_reply_ack` · `shop_attack_result`（outcome: captured） |
| UI | `src/ui/AttackAlert.js` | `role` 双视角（defender/attacker）合一面板：防守方还价滑条区（金额/倍数实时换算）；攻击方「✅ 同意还价（补差）/ ❌ 拒绝」复用护盘/认栽按钮位；`_verdict` 文案按角色（攻击方：收购成功/收购失败） |
| 样式 | `src/style.css` | `.attack-counter` 金色虚线按钮 + `.counter-panel` 滑条面板 + `.attack-counter-info` 冰蓝信息行 |

**资金守恒**：攻击方共付 `counterPrice`（发起时托管 bid + 成交时补差 price−bid），防守方全额收入 `counterPrice`——差额即收购溢价，双方账目闭合。

**Why the constraints**：还价下限 1.2 倍保证「还价只能加价不能杀价」；上限 2.0 倍防止漫天要价卡死谈判；每场一次防止无限拉锯拖垮 15 秒节奏。

### 12.6 街区众筹扩建 + 股份分红（GDD §4.3/§4.4 投资玩法）✅ 已实现

**玩家故事**：店主对黄金店发起扩建众筹 → 其他玩家入股 → 众筹成功店铺升级 +1、店主拿扩建资金 → 作为交换，店铺租金收益的 **40%** 进入分红池，**全体股东按持股比例长期分红**——平民玩家不收购店铺也能分享黄金店收益。

| 环节 | 规则 |
| --- | --- |
| 发起 | 仅**店主本人**，仅 **tier ≥ 2 特色店及以上**；目标 = 店铺身价 × 50%；期限 24 小时 |
| 入股 | **10 万金币 = 1 股**（整数倍）；每场众筹每账号可多次追加；资金托管进项目 |
| 成功 | 到期满额 / 提前满额 → **店铺等级 +1**（收益与身价提升）+ **众筹款全额归店主** + 状态转 `funded` |
| 失败 | 到期未达标 → **全额退款** |
| 分红 | 该店当前租金收益 × **40%** 每小时进分红池；股东可领 = 池 × 持股比例 − 已领累计，随时领 |
| 股份 | **不可转让**（GDD §4.4：初期不做自由交易市场） |
| 易主 | 店铺被踢馆成交 → 项目解散，股东退 **90% 原始投入**（10% 众筹风险折损，防套利） |

| 层 | 文件 | 实现 |
| --- | --- | --- |
| 数据 | `server/db.js` | `crowd_projects`（id/shop_id/owner_id/target/raised/dividend_pool/last_pool_at/deadline/status）+ `crowd_shares`（project_id/user_id/amount/claimed_pool，PK 复合） |
| 结算 | `server/crowd.js` | `createProject` / `invest`（满额自动提前成功）/ `claimDividend` / `disbandByShop`（易主解散钩子，被 `capital.resolveCapture` 调用）/ `tickCrowd`（60s：到期结算 + 分红池按店铺当前租金 40% 累积；启动时先跑一轮补停机期） |
| 路由 | `server/index.js` | `/api/crowd/create` / `invest` / `claim` / `list`（list 含每项目进度 + 我的股份 + 可领分红） |
| UI | `src/ui/CrowdPanel.js` | 面板：项目卡片（进度条/倒计时/入股按钮组 1/5/10 股）+ 我的股份行（可领分红一键领取）；入口 = 资产卡（自己的 tier≥2 店）「📋 众筹扩建」按钮 |
| 战报 | 全服弹幕 | 发起 / 成功 / 失败 / 解散四类通告 |

**经济闭环**：股东投入 → 店主拿扩建资金（店铺升值）→ 股东分 40% 租金长期回血；失败全额退款；易主解散 90% 退款——**三种结局资金全部可溯源，无系统印钞**。

### 13. 街头经济闭环

`server/treasure.js`，全部奖励数值由**服务端生成**，前端只负责拾取表现。

| 机制 | 触发 | 冷却 | 奖励 | 数据库 |
| --- | --- | --- | --- | --- |
| 金币雨 | `/api/game/collect { type: 'coin' }` | 450ms | ¥20K–80K，6% 暴击 ¥500K | `users.last_coin_at` |
| 财阀金币箱 | `/api/game/collect { type: 'box' }` | 45s | ¥800K–2M | `users.last_box_at` |
| 碰瓷 NPC | `/api/game/bully { npcId }` | **2 小时 / 每人 / 每 NPC** | ¥20M | `npc_claims (user_id, npc_id)` |
| 家族分红 | `/api/game/dividend` | 手动领取 | ¥60K/h 基础 + ¥120K/h/店 | `users.last_dividend_at` |
| 膜拜红包 | `/api/game/worship { userId }` | **1 小时 / 人** | ¥50K（仅当前全服首富可被膜拜，系统发放） | `worship_logs` + `transaction_logs` |

**离线分红计算（带衰减曲线）**（`dividendStatus(userId)`）：

网页端玩家不像客户端游戏能长时间挂后台——浏览器 tab 会被系统节流、会被用户关闭、移动端浏览器还会被 kill 进程。因此用**衰减曲线**把"离线越久单位收益越低"写进规则，配合站内护盘警报把玩家拉回：

```
ratePerHour  = 60_000 + ownedShopCount × 120_000       // 基础 + 每店加成
elapsed      = now - lastDividendAt                    // 真实离线时长

// 前 8 小时 100% 收益，8–24 小时线性衰减到 50%，24 小时后不再累积：
effectiveHours =
  elapsed < 8h                          →  elapsed
  elapsed < 24h                         →  8h + (elapsed - 8h) × (1 - (elapsed - 8h) / 32h)
  elapsed >= 24h                        →  12h   // 封顶 12 小时等效收益

pending      = floor(ratePerHour × effectiveHours / 3_600_000)
seconds      = Math.floor(elapsed / 1000)               // 展示用真实离线秒数
```

### 16. 远端玩家双行气泡 + 标签裁剪（Label Culling）✅ 已实现

WebSocket `players` 推送现在包含 `title` 字段（由 `buildNearbyList()` 从 DB 查询持有店铺数 → `titleFor()`）。
前端 `Player.js` 的头顶名牌 Sprite 渲染两行：**第一行昵称**，**第二行财富称号**（字号更小、颜色更淡），
始终朝向相机（`depthTest: false`）。

**裁剪已落地**：`main.js` `updateRemoteLabels()` 在 animate 每帧执行——距离分档（<10m 完整双行 / 10–50m 单行昵称 / >50m 隐藏）、`THREE.Frustum` 视锥剔除、最近 8 个完整气泡上限；私聊对象与踢馆攻击者强制保留完整标签；Canvas 仅在档位切换时重绘。

#### 标签裁剪：30 人同房间不遮挡

**问题**：30 个玩家在同一条街上同时走动，如果每个人头顶都显示"昵称 + 财富称号 + 帮会信息"双行甚至三行 → 屏幕上挂满了牌子 → 严重遮挡 3D 场景、找不到店铺、走路都看不清楚。

**分层裁剪策略**：

```
相机
 │
 ├─── 3 米内（贴脸）：显示完整双行气泡 + 完整称号
 │                    "👑 千亿财阀
 │                       全球经济唯一的爹"
 │
 ├─── 3 ~ 10 米：显示完整双行气泡，称号稍微缩小
 │                    "👑 千亿财阀
 │                       全球经济唯一的爹"   ← 字号 18px
 │
 ├─── 10 ~ 25 米：只显示昵称 + 称号缩写
 │                    "👑 千亿财阀"          ← 称号只留第一行
 │
 ├─── 25 ~ 50 米：只显示昵称（无称号）
 │                    "千亿财阀"
 │
 └─── 50 米外：完全隐藏头顶 Sprite，只保留 3D 角色模型

 以上阈值可调；动态场景下还叠加：
   - 每帧最多同时显示 8 个完整气泡（按距离排序取最近 8 个）
   - 屏幕外的玩家（Frustum 外）标签直接隐藏（相机视锥剔除）
   - 被建筑挡住的玩家（Occlusion Culling）标签隐藏（可选：需要 Three.js Frustum + BoundingBox 碰撞）
   - 当前正在和你私聊 / 正在踢你店的玩家 → 强制保留完整标签（不参与裁剪）
```

**实现要点**：

| 裁剪层 | 技术 | 实现位置 |
| --- | --- | --- |
| 距离裁剪 | 每帧遍历 `remotePlayers` → 算 `distanceToCamera.position` → 分档设置 sprite scale + 内容 | `main.js` animate 循环内 |
| 视锥剔除 | `camera.frustum.containsPoint(player.mesh.position)` → false 则 sprite.visible = false | 同上，可省一步算距离 |
| 上限裁剪 | 按距离排序 → 只对最近 8 个玩家启用完整双行，其他人只显示昵称 | 同上 |
| 强制保留 | 正在和我私聊的对象 / 正在被攻击的店铺 owner → 设 `_forceShow: true` 跳过裁剪 | `Player.js` 构造或 main.js 更新标签时 |
| 遮挡剔除（可选） | 用简单光线投射 `raycaster.intersectObject(scene.children)` 判断玩家 sprite 中心到相机是否被 `shopMeshes` 挡住 → 挡住则隐藏 | Three.js Raycaster，单帧 30 次 ray 约 0.1ms，对 60FPS 无影响 |

**标签内容分层**（CanvasTexture 内容动态生成）：

```
完整（3m 内）：
┌───────────────────┐
│  👑 千亿财阀       │  ← 大字号昵称 + emoji 前缀
│  全球经济唯一的爹   │  ← 小字号称号（灰色）
└───────────────────┘   Sprite 高度 120px

中等（10~25m）：
┌───────────┐
│ 👑 千亿财阀 │  ← 只留一行，称号只留第一阶
└───────────┘   Sprite 高度 60px

简略（25~50m）：
┌─────────┐
│ 千亿财阀  │  ← 只有昵称
└─────────┘   Sprite 高度 40px
```

> **关键权衡**：裁剪不是"少画"而是"有选择地画"——离得近的完整显示（社交信号：谁在我附近），离得远的简略显示（位置信号：有人在那边），完全看不到的就不画（性能信号：GPU 省下来画 3D 场景）。这样 30 人房间里最多同时有 8 个完整气泡 + 约 12 个简略昵称 Sprite + 10 个完全隐藏 → 屏幕上同时渲染的 CanvasTexture Sprite 不超过 20 个 → 遮挡大幅减少，GPU 压力也小。

### 19. 商业逻辑可行性评估 + MVP 美术策略 + 加载优化

#### 核心玩法商业逻辑可行性：中高（需防范刷金与死锁）

**最大亮点**：「跨线收购 × 15 秒护盘」制造的**短剧式爽感**。B 的 cafe 被 C 发起踢馆，B 有 15 秒焦虑窗口决定是砸 1.5× 身价护盘还是认栽丢店——这种"倒计时焦虑 + 金钱决策 + 全服围观"是本游戏 PvP 的灵魂。战报弹幕让隔壁房间的路人也能吃瓜，让单人行为变成公共事件，放大爽感。

**必须防范的三类风险**：

| 风险 | 场景 | 危害 | 对策 |
| --- | --- | --- | --- |
| **并发竞争** | B 和 C 同时 1ms 内对 cafe 发起踢馆 | 两次扣款 / 两条 pending 记录 / 保护期被覆盖 | DB 行级原子性 + 单事务（见 §12 并发安全子节）；禁止客户端以"我还没收到 result"为由重试 |
| **刷金** | 玩家用小号自踢自护：A 攻击自己的 cafe → 小号 B 护盘 → cafe 保护期 → A 再收租 | 凭空赚 baseIncome（店铺仍在 A 名下，只是期间无法被攻击） | 护盘时 defender 必须是**当前 owner**；发起攻击的 attacker 不能是 owner 本人（后端已拦截）；短期保护期无直接盈利，长期通过收租获益——利益链是单向的 |
| **离线分红套利** | 玩家攒 8 小时分红 → 快到点时用小号踢馆自己店铺 → 触发保护期的同时领取分红 | 分红按"持有店数"算，保护期不减持有 | 分红按"最后一次收租时间"追溯，不保护期豁免 |

#### MVP 美术：风格化低多边形（Stylized Low-Poly）

**明确策略：第一版（MVP）用程序化生成 + 风格化低多边形，不接入真实 GLB**。

| 对比项 | 真实 Blender GLB | MVP 程序化 + 低多边形 |
| --- | --- | --- |
| 美术制作成本 | 高（每栋建筑 2–8 小时建模） | **零成本**（`ProceduralStreet.js` 已有，按 `layout.js` 数据驱动） |
| 首屏加载体积 | 20–80 MB / 套 | **< 50 KB**（全部是运行时代码，无外部模型文件） |
| 秒进游戏 | 不行（需下载 + Draco 解码） | **可以**（npm run build 产物 = three 独立包 544 kB + 业务包 220 kB，gzip 合计约 219 kB；three 包长缓存，业务更新不影响其下载） |
| 风格统一度 | 依赖美术一致性 | 程序化建筑自动统一材质 + 随机扰动 |
| 可迭代速度 | 换一整条街需重导 GLB | 改 `layout.js` 数据 → 秒级热更新 |

**风格化低多边形的技术手段**（已在 `ProceduralStreet.js` 和 `Player.js` 中实现）：

- **材质**：MeshStandardMaterial + 粗糙 diffuse 颜色 + 无法线贴图 → 自带 Low-Poly 风格
- **建筑**：BoxGeometry 堆垛 + 随机屋顶三角形 → 青果巷白墙黛瓦的卡通感
- **玩家角色**：程序化 Box 拼身体 + CapsuleGeometry 头 + 走路动画 → 圆润可爱
- **商铺**：头顶 CanvasTexture Sprite emoji → 低成本识别
- **光照**：方向光 + hemisphere light + 阴影 = 统一卡通氛围

> 后续接入真实 GLB 时，走"替换资产"而非"替换系统"——`layout.js` 里的 `model: 'xxx.glb'` 字段留空时 fallback 程序化生成，有值时加载 GLB。两条路径并存。

#### 加载优化：分块加载（Chunk Loading / 渐进式加载）

**当前加载瓶颈**：所有建筑 / 室内 / 道具 Mesh 在 `WorldLoader.js` 首次 render 前一次性实例化 → 青果巷全场景约 55 栋建筑 + 18 家店铺室内 → 首屏等待 ~1.5 秒。

**分块加载方案**（MVP 后期优化项）：

```

┌──────────────────────────────────────────┐
│  30m 内（当前地块）：       完整 Mesh + 阴影 │  ← 必须立即加载
├──────────────────────────────────────────┤

├──────────────────────────────────────────┤
│  100m 外（远景）：          不加载 / Billboard │  ← 走过才加载
└──────────────────────────────────────────┘

异步加载顺序：
1. 玩家出生点周围 30m 内建筑（阻塞加载，保证秒进）
2. 30–100m 环形区域（requestIdleCallback 非阻塞）
3. 玩家走向下一个地块时，预加载它的邻居（提前 5 秒）
```

| 优化点 | 目标 | 当前状态 |
| --- | --- | --- |
| LOD 距离分片 | 30m 外隐藏门窗/店招/灯笼等细构件，三角面数量 -70% | ✅ `ProceduralStreet` 打 `userData.lod='detail'`，`main.js` 每 250ms 按相机距离切换 |
| 室内懒加载 | 进店时才构建 18 家店室内 | ✅ `InteriorManager._buildRoom(shopId)` 已实现 |
| 纹理 atlas | 所有商店 emoji / 名牌 Sprite 合一张 atlas | ❌ 不做（收益≈0，见 §20） |
| CanvasTexture 池 | 名牌 / 倒计时 / 弹幕 Sprite 复用 Canvas | ✅ 已实现池化复用 |

> 写库量按「写请求数 × 库体积」估算：sql.js 每次 `run()` 都把整份内存库导出后覆盖写盘。

结论：

- **300 在线（10 房 × 30 人）在正常动作节奏下是稳的**——广播节拍不漂（p95 1.01s）、业务接口 p95 < 61ms、零错误零意外断线，与「单后端支撑 300 在线」的 MVP 判定相符。
- **瓶颈是 sql.js 的写盘模型，不是 WS 或房间广播**：单进程写库上限约 **180–190 次/s**（≈5.3ms/次，含全库导出）；300 人同时高频点击（金币雨 450ms 冷却 ⇒ 理论 660 写/s）会把事件循环打满，全站延迟劣化到秒级。
- 折算预算：300 在线时全体写操作可持续总量 ≈ 180/s，即**平均每人每 1.7s 只能有 1 次写库动作**；超过就要换 `better-sqlite3`（WAL + 增量写）或把金币/任务类写入合并批处理。
- **浏览器 30 人同房 60 FPS 未达标（2026-11-17 已实测）**：用 `scripts/fps-test.mjs`（本机 Chrome 有头模式 + CDP，禁用 rAF 节流，`Emulation.setFocusEmulationEnabled` 强制前台）配合 `stress.mjs --cluster --rooms 1 --users 29` 聚团实测。两轮结果：**平均 36.3 FPS**（峰值 63.2，有周期性掉到 1–14）与**平均 10.4 FPS**（前 7 秒 20–53，随后持续 1 FPS，`document.hidden=false` 排除节流）。瓶颈在前端渲染，不在后端——同期后端广播 p95 1.01s、`/api/health` p95 9ms 均正常。
- **瓶颈已定位并做了第一轮优化（CPU Profiling + Player.js merge，2026-11-17）**：优化前 draw call **每帧 3042 次**（每秒 91263 次 ÷ 30 FPS），three.js 内部占 selfTime 35–42%，`uniformMatrix4fv` 单函数就 11–17%；**业务 JS 仅占 0.8%**——标签 CanvasTexture 重绘与遮挡剔除射线都不是瓶颈。根因：`Player.js` 每角色由 ~18 个独立 mesh 组装（头/眼×2/发/躯干/双臂/双手/双腿/双鞋），30 人 = 540 draw call；建筑多部件 + shadow pass 再翻一倍。
  - **第一轮优化**：`Player.js` 引入 `BufferGeometryUtils.mergeGeometries` 按材质合并同部件（眼睛左右→1 mesh、全部头发→1 mesh、躯干+裙摆→1 mesh），并把 Sphere/Capsule/Cylinder 的 segment 数砍半（Sphere 24×18→12×8、Capsule 6/12→4/6、Cylinder 24→12）。
  - **效果**：draw call 从 91263/s → **44111/s（-52%）**，30 FPS 下 **3042/帧 → 1470/帧**；selfTime `(idle)` 从 14% 涨到 **50.6%**（主线程 50% 时间闲等 GPU），`uniformMatrix4fv` 跌出 Top 30；FPS 平均 **36.3 → ~51**（排除 Chrome 被系统窗口遮挡导致的尾端 1 FPS 样本，前 18 个稳定样本平均 51.1，最低稳定值 42.7——此前周期性掉到 1–14）。
  - **剩余**：`ProceduralStreet.js` 建筑部件未动（贡献约一半 draw call），继续做建筑合并 + segment 降低预期 draw call 降到 ~1000、FPS 稳定 60+。

> **MVP 闭环判定**：当 `npm run build` 零 warning、`npm run server` 零 EPERM、浏览器 30 人同房间 60 FPS（🟡 第一轮优化后平均 ~51，未达线；第二轮动建筑可到 60+，见上）、单后端支撑 300 在线（✅ 已实测，见上「压测与帧率实测」）、玩家离开页面时护盘警报能即时提醒（本地通知已实现；完整离线 Push 待移动端适配与护盘窗口设计后再评估）—— 这条链路跑通了，就可以上小规模灰度（几十人）收集留存数据，再决定是否进大规模部署 + 美术接入 + MySQL 迁移。

## 接入真实 GLB 模型

有两种接法：**按建筑逐栋替换（推荐，保留既有玩法）** 与 **整场景替换**。

### A. 按建筑替换（推荐）

1. 把 Blender 导出的模型放到 `public/models/`，例如 `public/models/cafe.glb`。
2. 在 `src/data/layout.js` 给对应建筑加 `model` 字段（相对 `/models/` 解析，也可写 `/abs/x.glb` 或完整 http(s) URL）：

   ```js
   { id: 'cafe', kind: 'shop', shopId: 'cafe', side: 'north', z: -100, w: 12, d: 20, h: 6.2, floors: 2, model: 'cafe.glb' }
   ```

   不想改数据、想先整条街试模型：文件按建筑 `id` 命名（`cafe.glb`、`bakery.glb`…）放进目录，
   用 `?models=/models` 打开即可自动按 `<id>.glb` 匹配。

3. 模型朝向：朝街立面朝 `-x`（北侧建筑）/ `+x`（南侧建筑）。默认按 `d × w × (h + 1.2)` 等比缩放并居中贴地；
   若模型已经是真实尺度与原位，加 `modelFit: 'none'` 关闭自动适配。
4. 替换范围：只换该栋建筑的几何体——碰撞体按模型包围盒就地更新，店招 / 店铺悬浮图标 / 门口触发圈 /
   地图标注 / 可收购资产绑定全部沿用原逻辑（`group.userData.shopId` 不变，历史建筑的浮动名牌会跟到新屋顶高度）。
5. 回退：模型 404、解析失败或未配置 → 该栋保留程序化建筑（控制台一条 `[GLB] 保留程序化建筑（id）` 警告），
   其余场景不受影响。逐栋加载在首屏之后后台进行，不阻塞进入游戏；同一模型被多栋引用只下载一次。

### B. 整场景替换（`?glb=`）

1. 将 Blender 导出的整条街模型放到 `public/models/`，例如 `public/models/street.glb`。
2. 通过 URL 参数加载：

   ```
   http://localhost:5177/?glb=/models/street.glb
   ```

   也可以把路径写死到 [WorldLoader.js](src/scene/WorldLoader.js) 的 `_resolveGlbUrl()` 中。

3. 模型命名约定（用于自动识别）：

   | 用途 | 名称匹配 |
   | --- | --- |
   | 地面高度 | 含 `ground` / `floor` / `road` / `terrain` / `street` |
   | 建筑碰撞体 | 含 `wall` / `building` / `house` / `shop` / `store` |
   | 可点击店铺 | `userData.shopId`，或名称形如 `shop_cafe` / `shop-cafe` |

4. 支持 Draco 压缩（解码器从 gstatic CDN 加载）。
5. GLB 加载失败或未指定时，自动回退到内置程序化街道，并在页面提示「已切换到内置示例场景」。

室内房间目前由 `InteriorManager._buildRoom()` 统一程序化生成；接入真实室内模型时，
替换该方法内部实现即可，`enter / leave / colliders / interactives / spawn / exit` 的对外结构保持不变。

## 已知限制

- **无实景贴图 / 真实模型**：已支持 `layout.js` 的 `model` 字段逐栋替换 GLB（失败自动回退），但仓库未附带任何美术资源，
  `public/models/` 目前仅含占位说明文件，默认建筑与人物均为程序化几何体；位置按公开资料近似还原，细部（门窗样式、砖木构件）不等于实景。
- **建筑造型体系单一**：除石坊外，建筑共用一套「白墙黛瓦硬山」生成器，靠面宽、进深、层数、色差区分。
- **室内为统一布局**：所有店铺共用同一套室内结构，仅配色不同。
- **角色无骨骼动画**：只有走路摆臂，没有转身、跳跃落地、上下坡等姿态过渡。
- **其他玩家只在街道可见**：位置只在街道上报，进店后远端仍停在店门口；远端模型不播放走路摆臂，只做位置与朝向插值。（私聊不受此限制，见 §22。）
- **触摸 / 移动端未适配**：交互依赖键盘与 Pointer Lock。
- **店铺保护期全局共享**：同一店铺 5 分钟保护期在所有玩家视角都是倒计时，没有针对特定攻击方的"已防守过一次"语义。
- **金币雨 / 宝箱前端触发逻辑简陋**：服务端只负责定价，掉落位置和触发频率由前端决定，理论上可被逆向（但金额由后端冷值生成，无法篡改）。
- **SQLite 文件锁**：两个 Node.js 进程同时写 `qingguo.db` 时会 EPERM（sql.js WASM 全量覆盖写盘），测试时用 `DB_PATH` 环境变量隔离。
- **写库上限 ≈180–190 次/s（单进程）**：每次 `run()` 全量导出覆盖，压测实测 300 人在正常节奏下安全（65 写/s），全员高频点击会把事件循环打满、端到端延迟劣化到秒级；扩容优先级应为 `better-sqlite3`（WAL）> 写入批处理 > MySQL。
- **刷金与套利风险未完全闭环**：当前后端已拦截"攻击自己的店"和"非 owner 护盘"，但极端场景（多小号自踢自护、攒分红 + 保护期套利）理论上仍可发生，需在关键交易入口加更多校验规则（见 §19 商业逻辑评估风险表）。
- **膜拜红包是纯系统发放**：每人每小时 ¥5 万不扣首富的钱，属于通胀口子（按 1 小时一次约 ¥120 万/天/人）；若经济需要收紧，可改成首富出资或按旧玩家递减。
- **首富快照 30s 轮询**：`top1` 由 30s 轮询缓存，最坏情况下榜单变更到广播/膜拜校验有 ~30s 延迟；膜拜总是校验「缓存里的当前首富」，不会把红包发给已下榜的人。
- **秘书人设存在浏览器本地**：3 人设选择与静音开关存 `localStorage`（按账号 key），换浏览器或清缓存会重新选；不进数据库，不影响任何数值。
- **多进程并发安全依赖 DB 原子性**：当前单进程内存 `pending` Map 只是快路径；未来用 PM2 cluster 或多后端水平扩展时，必须补 Redis 分布式锁（`SET shop:lock:xxx token NX PX 5000`），否则同店铺踢馆仍会产生重复扣款。
- **标签遮挡剔除曾抛 `matrixWorld` 空指针（2026-11-16 已修复）**：Sprint 4 引入的 `_occlRay` 只调了 `set(origin, dir)` 没设置 `raycaster.camera`，而 `world.shopMeshes` 里混有店铺图标 Sprite（`WorldLoader._createShopMarkers` 把图标也 push 进可点击列表）；three.js 对 Sprite 求交必须读 `raycaster.camera.matrixWorld`，于是先反复警告 `THREE.Sprite: "Raycaster.camera" needs to be set` 再抛 `Uncaught TypeError: Cannot read properties of null (reading 'matrixWorld')`，桌面端每帧被 `showError` 弹红条。修复：`main.js` 创建 `_occlRay` 时同步赋值 `_occlRay.camera = camera`。**教训**：three.js 中任何 Raycaster 只要可能命中 Sprite，都必须先设置 `.camera`——`setFromCamera()` 会自动设，手动 `set(origin, dir)` 不会。

### 21. 资本轮回（Prestige）与永久天赋

`server/prestige.js` + `shared/prestige.js`（数值同源）+ `src/ui/PrestigePanel.js`（T 键面板）。

**轮回规则**：持有资产总身价（Σ 基础价 × 1.5^(等级−1)）≥ `PRESTIGE_THRESHOLD`（**500 亿**）时可轮回。
门槛约等于买下一家黄金店（八桂堂总部 500 亿）；不再要求「全收集」——18 家全收购（1 级）约 1.014 万亿，是门槛的 20 倍，
升级黄金店也能更快达标（金融中心 Lv.3 ≈ 1.125 万亿）。

```
点数公式  points = floor(总身价 / 5 亿)     // 每 5 亿身价 = 1 张传世黑卡（刚好过线 = 100 张）
参考产出  刚好过线 100 张 · 全收集（1 级）≈ 2,028 张 · 全满级盘 ≈ 10,270 张
轮回执行  settle 结算租金 → DELETE player_shops → balance=0
          → rebirth_count+1 → black_card_points += points → syncDerived（称号回落街头路人甲）
保留项    天赋 / 任务进度 / 拾取与碰瓷冷却 / 黑卡点数余额
拦截项    总身价不足 → 409；攻守任一方有进行中踢馆 → 409（先打完再轮回）
```

**天赋表**（各 5 级，升级价 `[30, 60, 120, 240, 480]` 张黑卡）：

| talentId | 名称 | 效果公式（level 为当前等级） | 满级效果 |
| --- | --- | --- | --- |
| `goldHand` | 点金手 | 暴击率 `6% + 4%/级`；暴击奖励 `50万 × (1 + 30%/级)` | 暴击率 26%、暴击 ¥125 万 |
| `capitalDomination` | 资本压制 | 收购价 / 装修价 `× (1 − 6%/级)`（**踢馆出价不受影响**，保 PvP 公平） | 收购 / 装修 7 折 |
| `idleRent` | 躺平收租 | 分红速率 `× (1 + 20%/级)` | 分红速率 ×2 |

**接入点**：

| 模块 | 改动 |
| --- | --- |
| `server/game.js` | `buildState()` 下发 `prestige: { totalValue, threshold, ready, pointsPreview }` 与 `assets[].acquirePrice`（折后收购价）；`acquire` / `upgrade` 按天赋折扣计价（战报显示实付金额） |
| `server/treasure.js` | `collect` 暴击率与暴击奖励读点金手等级；`dividendStatus` 分红速率乘躺平收租系数 |
| `shared/prestige.js` | 点数公式 + 3 棵天赋定义 / 定价 / 效果公式前后端同源，唯一事实来源 |
| `src/ui/PrestigePanel.js` | 总身价进度条（门槛百分比）+ 轮回两段式确认（防误触）+ 天赋卡（5 格等级点 + 升级按钮 + 还差几张） |
| `src/main.js` | `T` 键开关面板（与聊天互斥、锁指针与移动）、Esc 关闭链加入轮回面板、退出游戏时清理 |

**兼容性**：老库 `_migrateV2()` 已幂等补齐 `rebirth_count` / `black_card_points` / `talents_json` 三列，现有用户启动即生效。

### 收购公平性待解决问题（GDD §3.6）

以下问题在设计收购系统时必须明确：

1. **店铺是否可以被连续收购？** → 已设 5 分钟冷却 + 新店主 30 秒保护期 ✅
2. **店主离线时如何处理？** → 护盘窗口内店主回来仍可护盘；15 秒内无响应则店铺易主 ✅
3. **收购挑战期间是否允许第三人参与？** → 护盘窗口内只有店主可护盘；挑战发起后其他挑战者无法叠加（冷却机制拦住）
4. **收购失败后挑战者损失多少？** → 当前设计：收购溢价全部扣除，不退 ✅
5. **店铺是否存在保护期？** → 已实现（新购 30 秒 + 新收购 5 分钟冷却）✅
6. **店铺收益是否影响收购价格？** → 收购价格 = 基础价 × 收益系数（已实现 `server/economy.js` 中的 `acquisitionPrice()`）✅
